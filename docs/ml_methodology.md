# ML methodology

All benchmark results refer exclusively to simulated records. The positive class is the explicit synthetic ground-truth label. Investigator dispositions never become training labels automatically.

`ml.features.engineer` sorts transactions chronologically, scores all records at an identical timestamp against the same strictly earlier snapshot, and then updates history. An account's median uses at most its last 100 amounts; cold-start median is LKR 3,000. All rolling activity, elapsed time, device and merchant histories are account-specific, including when one customer owns multiple accounts. Training and online scoring both partition by `account_id`. The online interface excludes the scored transaction ID and all simultaneous/future records. Labels and scenario names are never model inputs.

The chronological split targets 60% train, 20% validation, 20% untouched test. Boundaries move forward to keep equal-timestamp groups in one partition; training rejects data without enough distinct timestamps. StandardScaler is fit on training only. Logistic regression is the deployed demonstration model. Random forest uses balanced class weights; isolation forest learns training negatives only. All comparisons use identical test samples. Seeded fitting and a hash of features, labels and seed identify a version.

The validation threshold maximizes F1 among candidates from 0.05 through 0.80 in 0.025 increments, subject to at most 15% review volume where feasible. Test data does not influence threshold selection. Threshold reports let users explore test-set operational trade-offs; selecting a new production threshold still requires fresh validation. Precision at capacity uses the top 5% of scores; workload assumes ten minutes per review.

Operational risk is exactly 100 times logistic probability, bounded at 0–100. It is not an arbitrary blend. The independent anomaly score is the percentile of an isolation score against training data, and is explicitly not fraud probability. Rule scores are separate transparent context. `FraudEngine(risk_bands=(25,50,75), rule_config={'amount_ratio':4,'hourly_count':3})` configures operational bands and main rule thresholds. Bands do not control alert creation: the validation-selected probability threshold does. Missing artifacts make service readiness fail; there is no silent model substitution.

The explanation is an exact linear attribution in log-odds: intercept plus the sum of standardized-feature × fitted-coefficient contributions equals the logistic decision output. Sigmoid of that output equals the displayed probability. Baseline is the training mean feature vector. This is a model-appropriate alternative to SHAP, not a causal explanation. Correlated features can redistribute attribution, and the baseline is not necessarily a real customer.

Drift uses training reference and held-out current windows. An explicit current window is merged with available history and deduplicated before chronological features are calculated, so window boundaries do not create artificial cold starts. Callers can supply full history with `drift_report(current, history=...)`; otherwise the model's stored dataset provides historical context. Numerical PSI uses training deciles and epsilon smoothing. PSI above 0.10/0.25 is a heuristic warning/critical threshold; KS statistics and p-values provide additional context. Categorical total-variation distance compares channels and merchant categories. Prediction drift and missingness are distinct outputs. Synthetic label coverage is 100%; arbitrary current windows have unknown coverage. Drift does not establish concept drift or authorize promotion.

Evaluation exports precision-recall and ROC chart arrays sampled to at most 100 points each. AUC metrics still use every held-out prediction. Curves are explicitly unavailable when the evaluation window lacks both positive and negative classes; the ROC-AUC metric is null in that case.

Artifacts are trusted-local joblib files; never load user-uploaded pickle/joblib. Save the artifact, raw dataset/config and reports together. Rollback restores an approved prior artifact and matching metadata, followed by readiness verification. There is no external MLflow server: this local versioned artifact mechanism is the simpler registry for this demo. Calibration on real financial populations is not established.

Run `python -m ml --transactions 100000 --customers 1000 --output reports/generated` to generate raw JSONL, an artifact and JSON evaluation, threshold, drift, quality, model, EDA, scenario-distribution and feature-importance reports. Separate `raw_transactions.jsonl`, `curated_transactions.jsonl`, `features.csv` and `labels.csv` preserve data-stage boundaries. Curated features exclude labels and scenario metadata; all join through transaction IDs. The pipeline-performance report records actual elapsed duration and artifact lineage. Small benchmark JSON reports can be committed; large generated data and binaries remain ignored. The CLI defaults to 100,000; the API quick-start uses 3,000. Larger populations reduce history density and may alter model performance. `backend/tests/test_ml.py` verifies malformed-value quarantine, consistent account age, timestamp-group split separation, future/target exclusion, train/serve parity, explanation reconstruction, deterministic generation, metrics, drift and persistence.
