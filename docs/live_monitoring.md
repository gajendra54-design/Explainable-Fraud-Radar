# Verified outcomes and monitoring investigations

Live performance is distinct from the synthetic held-out model benchmark. `GET /api/v1/monitoring/live-performance` evaluates stored predictions only against separately submitted verified labels. Raw simulation labels embedded in transaction metadata and investigator dispositions never enter this evaluation automatically.

Administrators submit `POST /api/v1/monitoring/verified-labels` with a `labels` list. Each item requires `transaction_id`, integer `label` (0 or 1), `source`, `evidence` and timezone-aware `verified_at`. The API rejects future verification dates, dates preceding the transaction, unknown transactions and duplicate IDs within a batch. A batch is atomic. Replaying the same label/source/evidence is idempotent. Conflicting labels return 409 and do not overwrite evidence. Corrections require a separately reviewed procedure outside this demo. Each newly accepted label creates an audit event. Authorization establishes who submitted the assertion; the application cannot independently prove the evidence's truth.

Live performance defaults to a 365-day transaction window, seven-day event-age maturity and at least 20 verified labels per model. Query parameters `window_days`, `maturity_days` and `minimum_labels` configure these assumptions. The response shows total and mature populations, immature records, label coverage and per-model metrics. Unknown labels stay excluded. A model with too few labels returns null metrics. Coverage below 80% marks available metrics provisional because selective labels can bias estimates. Seven days is a demo maturity assumption, not a guarantee every outcome has arrived. The response warns about a decline exceeding 0.10 F1 relative to the stored benchmark only when mature label coverage is at least 80% and the minimum sample count is met. Synthetic baseline and current population differences require investigation before interpreting a decline.

Authenticated users can read persisted monitoring investigations through `GET /api/v1/monitoring/incidents` and `GET /api/v1/monitoring/incidents/{id}`. Investigators and administrators create an investigation with `POST /api/v1/monitoring/incidents`, sending `title`, `summary` and `severity` (`warning` or `critical`). The server captures the active model's actual drift report using the latest 1,000 transactions and full account history. The stored snapshot includes model version and capture time. Clients cannot supply or overwrite the drift evidence.

`POST /api/v1/monitoring/incidents/{id}/events` accepts a `note` and status `Open`, `Investigating` or `Resolved`. Resolving requires `confirmed: true`. Investigating incidents cannot move backward to Open, and resolved incidents reject subsequent mutation. Each action appends an investigation event and a general audit event in the same transaction. No endpoint replaces a model or takes action against an account.

Migration `0003_monitoring.py` creates verified-label and monitoring-investigation tables. Models live in `backend/app/models/monitoring.py`, API validation and authorization in `backend/app/api/monitoring.py`, and coverage/maturity calculations in `backend/app/services/monitoring.py`. Dedicated tests exercise independence from raw labels, delayed maturity, partial coverage, degradation prerequisites, idempotency, atomic rejection, role restrictions and the complete persisted incident history.
